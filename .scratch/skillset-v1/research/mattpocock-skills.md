# mattpocock/skills — deep dive

## What it is

Matt Pocock's daily-driver skillset: ~20 "promoted" skills in `skills/engineering/` + `skills/productivity/`, shipped as a Claude Code plugin (`claude plugin install mattpocock-skills@claude-plugins-official`), a Codex/Copilot marketplace plugin, and editable copies via `npx skills add mattpocock/skills`. The pitch: "Approaches like GSD, BMAD, and Spec-Kit try to help by owning the process... These skills are designed to be small, easy to adapt, and composable." ([README](https://raw.githubusercontent.com/mattpocock/skills/main/README.md)) All per-repo behavior is externalized into config files that a one-time setup skill writes and every other skill reads.

## How it works

### The invocation split (the repo's one structural law)

Every skill is either **user-invoked** (orchestrator; `disable-model-invocation: true` in frontmatter + `policy.allow_implicit_invocation: false` in a sibling `agents/openai.yaml` for Codex) or **model-invoked** (reusable discipline; rich "Use when..." trigger phrasing). Rule: "A user-invoked skill may invoke model-invoked skills, but it can never reach another user-invoked one." Dependencies between skills are written as explicit tool calls, not `/name` prose: "Dependencies are expressed as an explicit instruction to **call the Skill tool** with the named skill... Naming the tool is what gets it fired" and "A step that needs two skills is two calls, not one call with two names: say so (`Call the Skill tool twice, for "grilling" and "domain-modeling"`)". Because `setup-matt-pocock-skills` is user-invoked, dependents phrase the pointer for the human: "tell the user to run `/setup-matt-pocock-skills`". ([.agents/invocation.md](https://raw.githubusercontent.com/mattpocock/skills/main/.agents/invocation.md))

### The engineering chain: artifacts and state

State between sessions lives **entirely in the issue tracker and repo files** — never in the skills. The skills themselves are stateless markdown.

| Skill (invocation) | Consumes | Produces | State location |
|---|---|---|---|
| `setup-matt-pocock-skills` (user, once/repo) | repo exploration + user answers | `docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md` (if triage installed), `docs/agents/domain.md`, `## Agent skills` block in CLAUDE.md/AGENTS.md; creates tracker labels | per-repo config files |
| `grilling` (model) | conversation | settled decision tree *in conversation* | none (ephemeral) |
| `grill-with-docs` (user) | conversation | same as grilling + inline `GLOSSARY.md`/ADR updates | user repo files |
| `to-spec` (user) | conversation + codebase | one spec **published to the tracker**, labeled `ready-for-agent` | tracker |
| `to-tickets` (user) | spec (or conversation) | vertical-slice tickets with blocking edges in the tracker | tracker |
| `implement` (user) | ticket reference | code + commit, via `tdd`, ending with `code-review` | code; ticket closed in tracker |
| `implement-spec` (user) | spec + ticket graph | whole spec on one integration branch via implementer/merger subagents | code; tickets closed in tracker |
| `code-review` (user+model) | diff since fixed point + spec + standards docs | two-axis findings report (no repo writes) | none |

- **grilling** works a "design tree" in **frontier rounds**: "The **frontier** is every decision whose prerequisites are already settled... Ask the whole frontier in one round: number each question and give your recommended answer. Then wait." Questions are formatted `❓ **Q1** ... ➡️ <recommended answer>` and "Word each question so 'yes' accepts your recommended answer." Fact-finding is delegated: "dispatch a sub-agent with a fresh context window to find it; don't ask the user for anything you could look up yourself." Done when "the frontier is empty." ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/grilling/SKILL.md)) NOTE: our installed copy is the older one-question-at-a-time version; main is the frontier design.
- **grill-with-docs** is a 2-line orchestrator: "Call the Skill tool twice, for 'grilling' and 'domain-modeling'." ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/grill-with-docs/SKILL.md)) Composition lives in the callees.
- **to-spec**: "Do NOT interview the user; just synthesize what you already know." Step 2 quizzes **seams**: "Existing seams should be preferred to new ones. Use the highest seam possible... The fewer seams across the codebase, the better - the ideal number is one. Check with the user that these seams match their expectations." Spec template: Problem Statement, Solution, an extremely long numbered User Stories list, Implementation Decisions, Testing Decisions, Out of Scope, Further Notes — with a durability rule: "Do NOT include specific file paths or code snippets. They may end up being outdated very quickly." (exception: a prototype snippet that "encodes a decision more precisely than prose can"). Published with `ready-for-agent` — "no need for additional triage". ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-spec/SKILL.md))
- **to-tickets**: breaks work into "**tracer bullet** tickets": "Each slice cuts a narrow but COMPLETE path through every layer (schema, API, UI, tests)... A completed slice is demoable or verifiable on its own... sized to fit in a single fresh context window." Escape hatch: "**Wide refactors are the exception**... sequence it as **expand–contract**... each batch its own ticket blocked by the expand, keeping CI green batch to batch." User quiz: "Does the granularity feel right? Are the blocking edges correct...?" Publishing: local = "one file per ticket under `.scratch/<feature-slug>/issues/<NN>-<slug>.md`, numbered from `01` in dependency order (blockers first)"; GitHub = "one issue per ticket in dependency order... Use the platform's native blocking relationship"; tickets get `ready-for-agent` ("agent-grabbable by construction"). Local ticket file: `**What to build:**` (user-perspective end-to-end), `**Blocked by:**`, `**Status:**`, acceptance-criteria checkboxes. ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-tickets/SKILL.md))
- **implement** is tiny (20 lines): fetch ticket from tracker, "Call the Skill tool with 'tdd' where possible, at pre-agreed seams", typecheck + single test files regularly + full suite once, "Once done, call the Skill tool with 'code-review' to review the work. Commit your work to the current branch." ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/implement/SKILL.md))
- **implement-spec** treats tickets as a **task graph**: "There is always a **frontier** of tickets which are ready to be grabbed." "Start every subagent with a fresh context window. Communication... should be sparse. Communicate primarily through **context pointers**... Don't duplicate information already available via pointers." Flow: exploration subagent (notes saved "in a directory outside the repo") → per-ticket implementer subagent in "its own worktree on its own branch" (rebased on integration branch, runs `tdd`) → merger subagent merges to integration branch → repeat on frontier change → final `code-review` on the branch → "Fix all issues raised by the code review in a single fresh implementer subagent." ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/implement-spec/SKILL.md))
- **code-review**: pins fixed point (`git diff <fixed-point>...HEAD`, verified resolvable + non-empty before spawning); finds the spec via "issue references in the commit messages → a path the user passed → a spec file under `docs/`, `specs/`, or `.scratch/` matching the branch name"; collects standards sources ("When `CODING_STANDARDS.md` or `CONTRIBUTING.md` exists, it must be on the list") plus a **fixed Fowler smell baseline** (12 smells, each "what it is → how to fix"; "The repo overrides... where it endorses something the baseline would flag, suppress the smell"; smells "always a judgement call"). Standards + Spec subagents run in parallel, each "Under 400 words", aggregated verbatim under `## Standards` / `## Spec`: "Do **not** merge or rerank findings... Reporting them separately stops one axis from masking the other." ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md))

### The `docs/agents/*.md` per-repo config contract

`/setup-matt-pocock-skills` is a "prompt-driven skill, not a deterministic script" that explores, presents findings section by section ("Lead each section with the recommended answer so the user can accept it in a word"), then writes ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/setup-matt-pocock-skills/SKILL.md)):

1. **`docs/agents/issue-tracker.md`** — from seed templates: GitHub ([source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/setup-matt-pocock-skills/issue-tracker-github.md)), GitLab, or local markdown ([source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/setup-matt-pocock-skills/issue-tracker-local.md)); anything else is freeform prose from the user. Each template is a full CLI cookbook: exact `gh` commands for create/read/list/sub-issue/blocking ("`gh issue create --blocked-by <n>`... Older `gh`: `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`"), comment/label/close, a "PRs as a request surface: no" flag read by `/triage`, and a **"Wayfinding operations"** section defining map/child-ticket/blocking/frontier/claim/resolve in tracker terms (local: map = `.scratch/<effort>/map.md`, tickets = `issues/NN-<slug>.md` with `Type:`/`Status:` lines, claim = "set `Status: claimed` and save before any work", frontier = "scan... for files that are open, unblocked, and unclaimed; first by number wins").
2. **`docs/agents/triage-labels.md`** — maps the 5 canonical roles (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`) to the repo's actual label strings ("Edit the 'Label in our tracker' column to match whatever vocabulary you actually use"). Written only when `triage` is installed ([source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/setup-matt-pocock-skills/triage-labels.md)).
3. **`docs/agents/domain.md`** — consumer rules: "Before exploring, read these: GLOSSARY.md... docs/adr/"; "If any of these files don't exist, **proceed silently**"; "use the term as defined in GLOSSARY.md. Don't drift to synonyms"; "If your output contradicts an existing ADR, surface it explicitly" ([source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/setup-matt-pocock-skills/domain.md)).
4. **`## Agent skills` block** in whichever of CLAUDE.md/AGENTS.md exists (never create the other): three one-line summaries, each with "See `docs/agents/....md`" pointers.

Consumers declare the dependency with different strength per [ADR 0001](https://raw.githubusercontent.com/mattpocock/skills/main/.agents/adr/0001-explicit-setup-pointer-only-for-hard-dependencies.md): **hard-dependency** skills (`to-tickets`, `to-spec`, `triage`) get the explicit pointer ("Without the mapping, output is wrong, not just fuzzy"); **soft-dependency** skills (`tdd`, `diagnosing-bugs`) just say "the project's domain glossary" in vague prose "to keep soft-dependency skills token-light".

### Wayfinder (plan > one session)

A map = one issue labeled `wayfinder:map`; work = child "decision tickets" ("questions whose resolution is a decision, not slices of a build"). Types: `research` (AFK, subagent + research skill), `prototype` (HITL), `grilling` (HITL, default), `task` (unblocks a decision). Map body is "an **index**, not a store" with sections Destination / Notes / Decisions-so-far / Not yet specified / Out of scope. "**Fog of war**": don't ticket what you can't state sharply — "The test is whether you can state the question precisely now, _not_ whether you can answer it now"; fog graduates into tickets as the frontier advances. Claim = assign before work ("so concurrent sessions skip it"); blocking uses the tracker's **native** dependency ("essential because it renders the frontier _visually_"); resolve = comment + close + "append a context pointer" to Decisions-so-far. "Never resolve more than one ticket per session", research excepted. Charting session "hand-resolves nothing" and fires research subagents onto "a throwaway `research/<name>` branch... it is never merged". ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/wayfinder/SKILL.md)) — this is the pattern our own MAP.md/tickets already mirror.

### Triage + agent briefs

State machine: category `bug`|`enhancement` + state `needs-triage → needs-info | ready-for-agent | ready-for-human | wontfix`. Steps: gather → recommend → **verify the claim** (reproduce the bug; for PRs check out and run tests) → grill if needed → apply outcome. `ready-for-agent` posts an **agent brief** ([AGENT-BRIEF.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/triage/AGENT-BRIEF.md)): "the original body and discussion are context: the agent brief is the contract." Rules: "**Durability over precision**... Don't reference file paths... Don't reference line numbers"; "**Behavioral, not procedural**"; complete testable acceptance criteria; explicit out-of-scope. Rejected enhancements are written to `.out-of-scope/` as a knowledge base ("that KB is for *rejected* requests, not built ones") ([OUT-OF-SCOPE.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/triage/OUT-OF-SCOPE.md)).

### tdd / domain-modeling / research / handoff (the model-invoked disciplines)

- **tdd**: tests "verify behavior through public interfaces, not implementation details"; "**Test only at pre-agreed seams**... No test is written at an unconfirmed seam"; anti-patterns: implementation-coupled, tautological ("Expected values must come from an independent source of truth"), horizontal slicing ("Work in **vertical slices** instead"). Notably: "**Refactoring is not part of the loop.** It belongs to the review stage (see the `code-review` skill)" ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/tdd/SKILL.md)).
- **domain-modeling**: challenge glossary conflicts inline, sharpen fuzzy terms, cross-check code; "update GLOSSARY.md right there. Don't batch"; "GLOSSARY.md should be totally devoid of implementation details"; ADRs offered only when all three hold: "Hard to reverse... Surprising without context... The result of a real trade-off". GLOSSARY format = **Term**: 1–2 sentence definition + `_Avoid_:` synonym list ([GLOSSARY-FORMAT.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/domain-modeling/GLOSSARY-FORMAT.md)); ADR = "an ADR can be a single paragraph", lazy creation ([ADR-FORMAT.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/domain-modeling/ADR-FORMAT.md)).
- **research**: "Spin up a **background agent**... Investigate against **primary sources**... Follow every claim back to the source that owns it. Write the findings to a single Markdown file, citing each claim's source" ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/research/SKILL.md)).
- **handoff**: handoff doc goes to `$TMPDIR` (not the repo), carries a "suggested skills" section, and "Do not duplicate content already captured in other artifacts... Reference them by path or URL instead" ([SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/handoff/SKILL.md)).

### SCOPE.md / GLOSSARY.md / repo hygiene (the skills repo itself)

- **SCOPE.md** is the contribution bar, not skill behavior: an issue stays open only if it clears "1. **Observed failure.**... A hypothetical improvement ('it would be better if...') does not clear this part. 2. **Fits the philosophy.** It does not match anything in `.out-of-scope/`" ([SCOPE.md](https://raw.githubusercontent.com/mattpocock/skills/main/SCOPE.md)). Each of the 8 `.out-of-scope/*.md` files records one rejected concept + why + prior issue numbers (e.g. [new-skills](https://raw.githubusercontent.com/mattpocock/skills/main/.out-of-scope/new-skills.md): "if you can compose the behaviour from existing skills, it doesn't get a new skill"; [mainstream-issue-trackers-only](https://raw.githubusercontent.com/mattpocock/skills/main/.out-of-scope/mainstream-issue-trackers-only.md): "Every issue-tracker backend hard-codes a CLI shape into the skills... permanent maintenance surface"; [subagent-recursion](https://raw.githubusercontent.com/mattpocock/skills/main/.out-of-scope/subagent-recursion.md): loop guards belong to "the harness", not skills).
- **GLOSSARY.md** (the repo's own) defines the set's shared vocabulary — **Issue tracker**, **Issue**, **Decision ticket**, **Triage role** — each with `_Avoid_` lists, plus "Flagged ambiguities" ("'backlog' was previously used to mean both the *tool*... Resolved") ([GLOSSARY.md](https://raw.githubusercontent.com/mattpocock/skills/main/GLOSSARY.md)). The skill's own GLOSSARY-FORMAT is applied to the repo itself.
- **CLAUDE.md** enforces inventory sync: promoted-bucket skills "must have a reference in the top-level README.md and an entry in `.claude-plugin/plugin.json`'s `skills` array... Skills in `misc/`, `in-progress/`, and `deprecated/` must not appear in either" ([CLAUDE.md](https://raw.githubusercontent.com/mattpocock/skills/main/CLAUDE.md)).
- **docs/<bucket>/<skill>.md** human docs pages follow a strict template ([.agents/writing-docs.md](https://raw.githubusercontent.com/mattpocock/skills/main/.agents/writing-docs.md)): fixed frame (`What it does` / `When to reach for it` / `Where it fits`), "the **defining constraint**" sentence, "surface the skill's leading word", branches "in a table or a list, never in a paragraph", `## Where it fits` names the role: "**chain step** (`grill-with-docs → to-spec → to-tickets → implement → code-review`), a **run-once setup**... **periodic maintenance**... or a **reach-for-it-anytime standalone**".
- Distribution: plugin manifests (`.claude-plugin/plugin.json` v1.3.2 ships exactly the promoted set) + [ADR 0002](https://raw.githubusercontent.com/mattpocock/skills/main/.agents/adr/0002-ship-as-a-claude-code-plugin.md) (ship as plugin) + `scripts/link-skills.sh` symlinking into `~/.claude/skills` and `~/.agents/skills` for maintainer dev.

## What to steal

Mapped to our goal: `npx skills`-installable personal skillset with greenfield/brownfield chains, configurable per project.

1. **The `docs/agents/*.md` config contract, wholesale.** Config-as-files that skills read beats per-skill assumptions, and we already run a local tracker this way. Adopt their template shape for our `docs/agents/issue-tracker.md`: conventions block + "publish to the tracker" recipe + "Wayfinding operations" section (map/tickets/claim/frontier/resolve). Their local-markdown template is nearly a spec for our existing `.scratch/` convention (map.md + issues/NN-slug.md + Status/Blocked-by lines).
2. **Chain artifact discipline**: conversation → spec (tracker, `ready-for-agent`) → tickets (tracker, blocking edges) → implement (per ticket, via tdd) → code-review (diff vs spec). State lives in tracker + repo files; skills stateless. This is exactly our greenfield flow; adopt the artifact table above as the contract in T006.
3. **Tracer-bullet sizing + expand–contract** (`to-tickets`): "sized to fit in a single fresh context window", demoable per slice, and the wide-refactor expand/contract/migrate-batches sequence is the single best brownfield pattern in the repo — make it part of our brownfield chain (T007).
4. **Durability rule for specs/tickets/briefs**: no file paths, no line numbers, behavioral contracts + testable acceptance criteria; prototype-snippet exception. Appears in `to-spec`, `to-tickets`, and AGENT-BRIEF — three independent confirmations it's load-bearing.
5. **Frontier-rounds grilling format**: numbered questions, recommended answer per question, "word each question so 'yes' accepts your recommended answer", sub-agent fact-finding, done-when-frontier-empty. Replace our installed one-at-a-time version.
6. **Two-axis code-review**: parallel Standards/Spec subagents, Fowler smell baseline with "repo overrides" rule, "under 400 words" each, no cross-axis reranking, spec discovery order (commit refs → arg → docs/specs/.scratch). Direct fit for our flow's close-out step.
7. **Seam agreement step** in `to-spec` + `tdd`'s "test only at pre-agreed seams" — pairs with `codebase-design` vocabulary we already have installed; this is the brownfield "where do tests go" answer.
8. **Hard vs soft dependency split** (ADR 0001) for our own setup-config pointer: only skills that would produce *wrong* output without config get the explicit "run setup" line.
9. **Invocation split + explicit Skill-tool-call dependency syntax** (`.agents/invocation.md`) for our authoring standard (T008): user-invoked orchestrators, model-invoked disciplines, "Call the Skill tool with 'x'" phrasing, two skills = two calls.
10. **Repo-hygiene patterns for OUR skills repo**: SCOPE-style acceptance bar (observed failure), one-file-per-rejected-idea `.out-of-scope/` KB, glossary with `_Avoid_` lists, CLAUDE.md inventory-sync rule (README + manifest must match promoted set), docs-page template's fixed frame for our READMEs.
11. **Wayfinder decision-ticket mechanics** — we already run it; adopt their refinements: "index, not store" map body, fog-of-war graduation test ("can you state the question precisely now"), claim-before-work, resolution = comment + close + pointer.
12. **Context-pointer communication** from `implement-spec` for our multi-agent runs ("Don't duplicate information already available via pointers").

## What to skip

1. **GitHub/GitLab tracker templates + plugin/marketplace distribution**: we decided on the local markdown tracker and `npx skills` (MAP). Keep only the local template as our seed; revisit native-blocking recipes only if we move to GitHub Issues. Multi-harness plugin manifests remain an open MAP item, not a v1 copy.
2. **`docs/` human-docs-pages machinery**: it exists to publish to aihero.dev and cut cognitive load for a public audience. Our audience is the owner; README-level entries suffice. Steal the template's *ideas* (defining constraint, branch-as-table, "Where it fits"), not the pipeline.
3. **`triage` + `.out-of-scope/` KB as-is**: designed for a public repo receiving external issues/PRs. We have no external request flow. Consider a reduced version (just `ready-for-agent`/`ready-for-human` status lines on local tickets, which to-tickets already emits) and skip needs-info/wontfix machinery, PR-as-request-surface, and AI-disclaimer comments.
4. **`implement-spec`'s worktree-per-ticket + merger-subagent orchestration**: heavy machinery for parallel subagents; our v1 flow is single-operator, and prime-agent gives us concurrency without worktrees. Adopt the frontier/task-graph *thinking*; defer worktree orchestration until we actually run parallel implementation.
5. **`ask-matt` router**: valuable when 20 skills need routing; our set will be smaller and MAP.md is our router. Revisit if the catalog grows.
6. **Peripheral skills** (`retro`, `wizard`, `pr`, `wait-what`, `teach`, `to-questionnaire`, `quiz`, `writing-for-agents`): useful but outside the v1 flow; park as backlog, not chain members.
7. **Strict "no new skills ever" posture**: right for a public one-maintainer catalog, wrong for a personal skillset under active greenfield construction. Keep the *observed-failure* bar for changing skills, drop the closed-catalog rule.
8. **`scripts/link-skills.sh`**: maintainer-dev symlink tool; we install via `npx skills`, no need.

## Surprises & open questions

1. **Our installed copies are all stale vs main** (17/17 differ; `implement-spec` absent; installed `grilling` is a superseded design). We "run these skills daily" on old versions — worth an `npx skills update` pass before judging them.
2. **Orchestration skills are almost empty on purpose**: `grill-with-docs` = 2 lines, `grill-me` = 1 line, `implement` = 20 lines. All substance sits in model-invoked callees. Supports our plan to keep orchestrators thin and port only disciplines.
3. **`tdd` explicitly evicts refactoring from the loop** and routes it to `code-review` — the skills are coupled by design; porting `tdd` without `code-review` loses half the loop.
4. **The issue tracker is the only inter-session database** — even for local markdown, wayfinding defines claim/frontier/resolve as file operations. No skill keeps state in its own folder; nothing needs a daemon.
5. **Wayfinder research findings live on throwaway branches "never merged"** — resolution comments are canonical; assets are linked, not pasted. A deliberate anti-duplication stance we should mirror in our research files.
6. **Open Q for T005/T006**: greenfield entry point — Matt's chain starts from a conversation (`grill-with-docs`) with no greenfield scaffold skill (no project-init/template step). Do we add one, or keep their "setup configures, conversation starts work" split?
7. **Open Q for T007**: brownfield — `to-tickets`' expand–contract + `improve-codebase-architecture` survey (HTML report → grill a candidate) look like the core; is `triage`-style agent-brief authoring worth porting as the handoff format between our research/spec and implementation sessions?
8. **Open Q**: `implement-spec` assumes a harness with background subagents and worktrees (Claude Code). Our harness has both via PTC; decide in T006 whether v1 `implement` is single-session `implement` or a simplified `implement-spec`.
