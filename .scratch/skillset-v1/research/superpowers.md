# Superpowers (obra/superpowers) — research notes

Ticket: T001 · Surveyed 2026-10-29 · Plugin version at survey: 7.0.1 · Stars 308,508, MIT, actively pushed (api.github.com/repos/obra/superpowers)

## What it is

A complete agent software-development methodology shipped as a skills plugin: 15 skills covering brainstorm → design → plan → subagent-execution → review → finish, plus one bootstrap skill injected at session start that makes the rest auto-trigger. Same repo publishes to ~16 harnesses (Claude Code, Codex App/CLI, Cursor, Gemini CLI, OpenCode, Pi, Devin, Copilot CLI, Antigravity, Hermes, Kimi, Muse, …) via per-harness plugin manifests over one shared `skills/` tree. By Jesse Vincent / Prime Radiant. (https://raw.githubusercontent.com/obra/superpowers/main/README.md)

## How it works

### 1. The auto-trigger is ONE hook, not machinery

- `hooks/hooks.json` registers exactly one hook: `SessionStart` with matcher `"startup|clear|compact"` — so the bootstrap re-injects on fresh start, after `/clear`, **and after compaction** (https://raw.githubusercontent.com/obra/superpowers/main/hooks/hooks.json).
- The hook script `hooks/session-start` reads `skills/using-superpowers/SKILL.md` from disk, JSON-escapes it, and emits it as context wrapped in `<EXTREMELY_IMPORTANT>You have superpowers. …For all other skills, use the 'Skill' tool:</EXTREMELY_IMPORTANT>`. It sniffs platform via env vars (`CURSOR_PLUGIN_ROOT` / `CLAUDE_PLUGIN_ROOT` / `MUSE_PLUGIN_ROOT` / `COPILOT_CLI`) and emits the JSON shape each platform wants: Cursor `additional_context` (snake_case), Claude Code `hookSpecificOutput.additionalContext`, SDK-standard top-level `additionalContext` (https://raw.githubusercontent.com/obra/superpowers/main/hooks/session-start).
- So "auto-triggering skills" = session-start injection of one routing skill + model-invoked `Skill` tool thereafter. Every other skill just sits in `skills/<name>/SKILL.md` with a routing-oriented frontmatter `description`; the model loads it when the bootstrap rule fires. No hooks per skill, no code paths.
- Per harness, injection differs but the architecture doesn't: Pi has a native extension injecting bootstrap "at session startup and again after compaction" (README, Pi section); OpenCode ships a JS plugin doing skills registration + bootstrap via chat-message transform, dual-compatible with OpenCode V1/V2 (https://raw.githubusercontent.com/obra/superpowers/main/.opencode/plugins/superpowers.js). Porting doc states the invariant: "**The bootstrap is the entire integration.** Without it, the skill files are inert — present on disk, never invoked." (https://raw.githubusercontent.com/obra/superpowers/main/docs/porting-to-a-new-harness.md)

### 2. The bootstrap skill: `using-superpowers`

Content of `skills/using-superpowers/SKILL.md` (https://raw.githubusercontent.com/obra/superpowers/main/skills/using-superpowers/SKILL.md):

- Routing rule, stated absolutely: "If you think there is even a 1% chance a skill might apply to what you are doing, you ABSOLUTELY MUST invoke the skill." and "**Invoke relevant or requested skills BEFORE any response or action** — including clarifying questions, exploring the codebase, or checking files. If it turns out wrong for the situation, you don't have to use it."
- Precedence: "User instructions (CLAUDE.md, AGENTS.md, …) take precedence over skills, which in turn override default behavior."
- Priority ordering: "process skills come first — they set the approach, then implementation skills … 'Let's build X' → superpowers:brainstorming first"; "'Fix this bug' → superpowers:systematic-debugging first".
- A 12-row "Red Flags" table mapping rationalizations to rebuttals ("This is just a simple question" → "Questions are tasks. Check for skills." / "I remember this skill" → "Skills evolve. Read current version.").
- `<SUBAGENT-STOP>`: subagents dispatched to execute a specific task ignore the skill (stops infinite skill-check recursion).
- Platform adaptation: per-harness tool-name mapping lives in `skills/using-superpowers/references/<harness>-tools.md` (claude-code, codex, gemini, pi, antigravity, hermes, muse). Porting rule: "Skills name actions, not tools" — skill bodies are never edited per harness; only the mapping file and the injector change (porting-to-a-new-harness.md).

### 3. The chain: brainstorm → spec → plan → execute → review → finish

Each stage is one skill; the artifact each hands forward is a **committed markdown file at a fixed path**.

1. **brainstorming** (`skills/brainstorming/SKILL.md`). Description: "You MUST use this before any creative work". Flow: read the codebase before asking anything ("Never ask what the project or their context already answers"); first message echoes the request + exactly one open question; Socratic interview, one question per message; incremental "play back" in ~200–300-word chunks; then **Lay out the approaches** — "Present the two or three [ways of building it] … Recommend one and say why"; then **Size the Work** (small change → short design; project → full design). Artifact: design doc committed to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` covering "intent and the why / goals, non-goals, anti-goals / constraints / approaches / the parts of the how they decided / what's left to the builder". Quality gate before handoff: a **builder check** — dispatch a fresh subagent with `builder-check-prompt.md` ("Report only the questions you'd still need answered before you could plan this well") and sort its questions into answered / minor / theirs. Enforcement: `<HARD-GATE>Nothing gets built until your human partner approves the design doc … After the design doc is approved, the next step is the plan: invoke superpowers:writing-plans and no other skill.</HARD-GATE>`. Escape hatches: user opt-out, and "spikes" (throwaway builds, no tests, must re-enter the gate to keep).

2. **writing-plans** (`skills/writing-plans/SKILL.md`). Frame: "Write implementation plans for an engineer who has not seen this codebase or this spec … What they cannot know is what you decided: which files, which names and signatures, which values from the spec, which tests prove each task." Artifact: `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md` with a mandatory header: Goal / Architecture / Tech Stack / **Spec:** backlink ("the plan argues from the spec, so the spec travels with it"), **Global Constraints** (spec's exact values "copied verbatim"), **Review Focus** ("the five input classes or failure modes the spec implies but no task's tests exercise"), and a literal instruction line telling the executor to use subagent-driven-development or executing-plans. Task format: exact Files (Create/Modify/Test paths), an **Interfaces** block ("Consumes / Produces … exact function names, parameter and return types. A task's implementer sees only their own task; this block is how they learn the names and types neighboring tasks use"), then checkbox steps, each "one action with a checkable result" (write failing test → run it → implement → run → commit). Step test: "A step is done when the implementer can write exactly one reasonable thing from it." Self-review checklist includes **proportion**: "A plan longer than the code it describes has written the code instead." Handoff: user reviews plan and picks executor — subagent-driven (thorough, fresh context per task) vs native/inline (cheapest, one final review) — with a one-sentence recommendation from the controller.

3. **using-git-worktrees** (`skills/using-git-worktrees/SKILL.md`). Detect existing isolation first (`git rev-parse --git-dir` vs `--git-common-dir`, submodule guard), prefer the harness's **native** worktree tool, fall back to `git worktree add` into `.worktrees/` only if none. "Never fight the harness."

4. **Execution, two variants sharing one workspace format**:
   - **subagent-driven-development** (`skills/subagent-driven-development/SKILL.md`, "SDD"): the controller dispatches a **fresh implementer subagent per task**, then a **fresh task reviewer** per task, then one whole-branch final review. Mechanics:
     - Per-plan scratch workspace at git-ignored `.superpowers/sdd/<plan-basename>/` (via `scripts/sdd-workspace`), holding the **ledger** (`progress.md`, first line `# SDD ledger — plan: <path>`), task briefs, implementer reports, review packages. Rationale: "Conversation memory does not survive compaction. …controllers that lost their place have re-dispatched entire completed task sequences — the single most expensive failure observed." "After compaction, trust the ledger and `git log` over your own recollection."
     - Continuous execution: "Do not pause to check in with your human partner between tasks." "**Rulings, not stalls.** A running plan does not wait on a human… Record every decision in the ledger as `Ruling: <what you decided> — <why> — <what it costs if wrong>`." Exactly four stops: irreversible/destructive op; security-sensitive; side effect outside the worktree; plan so broken every path is a guess.
     - Dispatch: `scripts/task-brief PLAN_FILE N` extracts one task's text to a file — "Never make a subagent read the whole plan file." Dispatch prompt = scene line + brief path + cross-task interfaces + ambiguity resolutions + report path. Implementer writes a full report to a report file and returns only a ≤15-line status contract: `DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT`, commits, one-line test summary, concerns (implementer-prompt.md).
     - Context hygiene is explicit: "A real session's dispatch hit 42k chars of which 99% was pasted history"; "Everything you paste into a dispatch prompt … stays resident in your context"; "Hand artifacts over as files."
     - Review: `scripts/review-package PLAN_FILE BASE HEAD` writes commit list + stat + full diff to a file (BASE recorded per task, "never `HEAD~1`, which silently truncates multi-commit tasks"); reviewer gets brief + report + diff file + Global Constraints verbatim; returns **two verdicts** — spec compliance (✅/❌ plus ⚠️ cannot-verify-from-diff items) and code quality (Approved/Needs fixes) with Critical/Important/Minor findings (task-reviewer-prompt.md). Anti-gaming rules in the template: "Do Not Trust the Report … 'left it per YAGNI' … is the implementer grading their own work"; "never instruct a reviewer to ignore or not flag a specific issue" (controller-side pre-judging forbidden).
     - Fix loop (`references/fix-loop.md`): rounds 1–3 **resume the same implementer** with findings; round cap + circuit breaker; re-review is **scoped** (`re-review-prompt.md`: "verdict each finding and inspect the fix diff — nothing else"), on cheap-to-mid models; past the cap the controller adjudicates and every ruling is a ledger line.
     - Model selection ladder: "Use the least powerful model that can handle each role"; implementation from complete plan text = cheapest tier; final whole-branch review = most capable model ("dispatch it on the most capable available model, not the session default"); "Turn count beats token price" (cheap models take 2–3× turns).
     - Workers are forbidden to spawn subagents: "never spawn a reviewer to check your work … A reviewer you spawn duplicates that review at full cost" (implementer-prompt.md); the rationalization table calls a worker-spawned reviewer "a duplicate seat … a defect to flag, not rigor".
   - **executing-plans** (`skills/executing-plans/SKILL.md`): same plan, same ledger/workspace format ("so a plan can change executors mid-flight"), but the session implements inline. TDD is the per-task gate; `scripts/task-start`/`scripts/task-done` bracket each task — task-done runs the task's test command and "only if they pass — appends the completion line to the ledger". A **completion contract**: every named test ran and output was read, every `Expected:` line compared, every deviation ledgered. Final review uses the same `code-reviewer.md` on the most capable model; Critical/Important get **one** fix pass, each fix verified RED→GREEN ("A fix without a test that failed first is not verified"); Minors are ledgered "deferred", never fixed silently. Final message must carry exhaustive "Rulings I made" and "Deferred minors" lists — "Your final message is the only place the decisions you took on your human partner's behalf … reach them."

5. **Cross-cutting skills**:
   - `test-driven-development`: "NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST … Write code before the test? Delete it." Verify-RED is mandatory ("If you didn't watch the test fail, you don't know if it tests the right thing").
   - `systematic-debugging`: 4 phases, Iron Law "NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST", instrument component boundaries before fixing (skills/systematic-debugging/SKILL.md).
   - `verification-before-completion`: "NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE"; 5-step gate IDENTIFY/RUN/READ/VERIFY/claim; claims table ("Tests pass" requires "Test command output: 0 failures", not "Previous run").
   - `requesting-code-review` + `code-reviewer.md`: dispatch template with placeholders; read-only review; "The spec is a vision document … a reasonable person's expectation is a requirement, and a spec's silence is not permission"; mandatory "**Declined to judge**" list — "list every behavior you considered and set aside … The executor rules on each line; nothing you set aside is dropped silently."
   - `receiving-code-review`: forbids "You're absolutely right!"; verify against codebase before implementing; if any item unclear, stop and ask about all before implementing any.
   - `finishing-a-development-branch`: full suite must be green first; detect repo/worktree/detached-HEAD; exact 3-option menu (merge locally / push+PR / keep).
   - `dispatching-parallel-agents`: "Dispatch one agent per independent problem domain", only when no shared state.
   - `diagnosing-superpowers`: post-hoc autopsy — reads the session transcript, reports with "line-level evidence", packages a scrubbed bug-report bundle (skills/diagnosing-superpowers/ + prompts/).
   - `writing-skills`: "**Writing skills IS Test-Driven Development applied to process documentation** … If you didn't watch an agent fail without the skill, you don't know if the skill teaches the right thing" — baseline pressure-tests with subagents, then RED/GREEN/REFACTOR on skill text (skills/writing-skills/SKILL.md).

### 4. Packaging, manifests, versioning

- One shared `skills/` tree; per-harness manifests: `.claude-plugin/plugin.json` (+ `marketplace.json` pointing at `./`), `.codex-plugin/plugin.json` (adds `"skills": "./skills/"`, `"hooks": {}`, rich `interface` metadata), `.cursor-plugin/`, `.devin-plugin/`, `.kimi-plugin/`, `.muse-plugin/`, `.antigravity-plugin/`, `.hermes-plugin/` (python), `.agents/plugins/marketplace.json`, `gemini-extension.json`, `.opencode/`, `.pi/` (tree listing: https://api.github.com/repos/obra/superpowers/git/trees/main?recursive=1).
- Codex content is mirrored into OpenAI's official marketplace repo by `scripts/sync-to-codex-plugin.sh` (rsync + PR against `prime-radiant-inc/openai-codex-plugins`, "Deterministic: running twice … produces PRs with identical diffs").
- Version sync across all manifests via `.version-bump.json` + `scripts/bump-version.sh` (README, Muse section).
- CI-ish guards in `tests/`: `tests/skill-size/test-skill-size.sh` fails if any SKILL.md ≥ 20,000 bytes — "After a compaction, Claude Code re-attaches each invoked skill truncated to 20,000 characters (#2481)"; heavy skill content lives in `references/` read on demand (progressive disclosure). Behavior evals live in a separate repo (superpowers-evals, driven by "Quorum" through real coding-agent CLIs) — see AGENTS.md.
- AGENTS.md contributor rules: 94% PR rejection rate; skill prose is treated as "carefully-tuned behavior-shaping code" — "PRs that restructure, reword, or reformat skills to 'comply' with Anthropic's skills documentation will not be accepted without extensive eval evidence" (https://raw.githubusercontent.com/obra/superpowers/main/AGENTS.md).

### 5. What is Claude-Code-specific vs portable

- Portable (works anywhere with file-read + subagents + bash): the entire skills tree, the artifact chain (spec/plan/ledger paths), prompt templates, review contracts, scripts.
- Harness-bound: SessionStart hook + re-injection on `clear|compact` (hook semantics differ per harness — Hermes "has no post-compaction hook, so a very long session that compacts over its first turn loses the bootstrap", README); the `Skill` tool itself (Pi "has native skills, so no compatibility `Skill` tool is required"); subagent/tool names per harness (references/<harness>-tools.md); Claude Code's 20k-char skill re-attach truncation (motivates the size test); `CLAUDE_PLUGIN_ROOT`-style env sniffing in the hook.
- Notably, AGENTS.md defines a **rejection bar for integrations**: "These are not real integrations and will be closed: … Wrapping with `npx skills` or similar at-runtime shims; Anything that requires the user to opt in to skills per-session." The acceptance test for any harness: send "Let's make a react todo list" and `brainstorming` must auto-trigger before any code.

## What to steal (mapped to our greenfield/brownfield flow)

1. **Bootstrap + router pattern.** One entry skill injected at session start (and after compaction) containing: the invoke-before-acting rule, process-before-implementation priority, a red-flags/rationalization table, and a subagent-stop clause. For us: each chain (greenfield/brownfield) gets a thin entry skill whose description makes it route first; the chain skills stay on disk. Skip the ALL-CAPS maximalism if we want, but keep the absolute rule + precedence order (user > skills > default).
2. **Artifact chain with fixed paths and backlinks.** spec → `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`; plan → `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`; plan header carries `Spec:` backlink + Global Constraints (verbatim values) + Review Focus. Adopt verbatim for our greenfield chain (brownfield: swap brainstorming's "look before you ask" front-loading deeper). Specs/committing artifacts is what makes resumability and review possible.
3. **Plan format.** Interfaces (Consumes/Produces with exact signatures), steps each "exactly one reasonable thing", checkbox RED→GREEN step skeletons, and the proportion check ("a plan longer than the code it describes has written the code instead") + 5-point self-review. This is directly our T006/T007 target shape.
4. **Execution workspace + ledger.** Git-ignored per-plan workspace, ledger file whose first line identifies its plan, append-only `Task N: complete (…)` lines, `Ruling:` lines with "what it costs if wrong", "trust the ledger and git log over your own recollection" after compaction. Prime-agent has the same compaction hazard; this is the cheapest insurance there is.
5. **Subagent dispatch discipline.** Brief files instead of pasting plan text (script-extracted), report files + ≤15-line status contract with four named statuses, diff handed to reviewers as a pre-generated package file, explicit per-role model selection ("an omitted model inherits the session's … which silently defeats this section"), "turn count beats token price", never dispatch parallel implementers on one tree, never let workers spawn reviewers.
6. **Review contracts.** Dual verdict (spec compliance + code quality), ⚠️ cannot-verify channel, Critical/Important/Minor calibration with named definitions, "spec is a vision document" grading, "Declined to judge" list, scoped re-reviews after fix rounds with a round cap and breaker, re-grade findings by effect before gating. Drop into our code-review stage nearly as-is.
7. **The small guardrail skills**: verification-before-completion and receiving-code-review are ~1-page each and composable into any chain we ship.
8. **Skill-authoring discipline** (feeds T008): skills name actions not tools (portability), <20k-byte SKILL.md with `references/` for progressive disclosure, routing-quality descriptions, pressure-test skills with subagents before shipping (baseline → with-skill), an acceptance-test prompt per chain ("Let's make a react todo list" equivalent: "build a tiny REST API" should route to brainstorming).
9. **Multi-manifest hygiene for later (T009/multi-harness note)**: `.version-bump.json` + bump script keeping N manifests in sync; deterministic sync script opening PRs into marketplace repos.
10. **diagnosing-superpowers-style autopsy**: a skill that reads a session transcript and reports what went wrong with evidence — cheap to write, high value when a chain misfires.

## What to skip (and why)

- **The 16-harness plugin matrix.** Each manifest, injector, and per-harness test suite is a real maintenance surface (sync scripts, polyglot Windows hooks, platform-specific JSON shapes). We install into prime-agent (and possibly a couple more later) — write one bootstrap injector per harness we actually use, not preemptively.
- **Visual companion** (brainstorming's browser mockup server): a whole subsystem — local server, auth hardening, WS protocol, telemetry opt-out — for optional mockups. Out of scope for v1.
- **HARD-GATE ALL-CAPS voice.** The gate concept (no building before spec approval) is worth adopting; the `<EXTREMELY-IMPORTANT>` shoutiness is their tested tuning, and they explicitly warn content is eval-tuned — imitate the structure, write our own wording.
- **Their contributor governance** (AGENTS.md PR rules, "human partner" terminology): repo-specific policy, not methodology.
- **Per-harness tool-mapping references**: needed only when we port to other harnesses.
- **Eval-lab machinery** (Quorum/Gauntlet): impressive but heavy; our scale says subagent pressure-tests + a size lint are enough for now.

## Surprises & open questions

- **"Auto-triggering" is just one SessionStart hook + one injected router skill.** The rest is prose engineering: descriptions tuned for routing, rationalization tables, hard gates. Nothing is enforced by code — if the bootstrap is lost (e.g., Hermes after compaction), the whole methodology silently evaporates. Our equivalent risk: prime-agent sessions that never load our entry skill.
- **The spec↔plan↔ledger file spine is the real product.** Skills are persuasive wrappers around a boring, robust artifact chain — that's the part that survives compaction, crashes, and harness swaps, and the part most worth copying wholesale.
- **They document their failures inside the skills** ("a real session's dispatch hit 42k chars of which 99% was pasted history"; "controllers … re-dispatched entire completed task sequences — the single most expensive failure observed"). Stealing the habit: our skills should cite the concrete failure each rule prevents.
- **Workers spawning reviewers is treated as a defect**, not extra rigor — duplicate review seats cost real money. Relevant to how we spec review stages.
- **Tension with our own distribution choice**: superpowers' AGENTS.md classifies `npx skills`-style installs as "not real integrations" precisely because they don't guarantee the bootstrap. `npx skills add ivanDsky/skills` gives us file placement, not auto-trigger — we still need a per-harness bootstrap story (in prime-agent's case, prompt/memory injection or the user's harness config).
- **Open:** does the ⚠️ cannot-verify + cap-parked-findings hygiene translate to solo inline work, or does it need SDD's controller/reviewer split? (Their executing-plans re-grades findings by effect itself — suggests it does.)
- **Open:** their skill descriptions are aggressively absolute ("You MUST use this before any creative work"). We should pressure-test whether that voice is load-bearing (their evals say the content is tuned) or portable to calmer descriptions.
- **Note on numbers:** 300k-star claim verified — 308,508 stars, 27,438 forks as of 2026-10-29 (https://api.github.com/repos/obra/superpowers). README's "the skills trigger automatically" oversells: only the router is injected; everything else is model-initiated.
