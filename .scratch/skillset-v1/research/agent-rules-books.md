# agent-rules-books — survey (T011)

Repo: https://github.com/ciembor/agent-rules-books (3,139 stars, MIT, v0.6, last push 2026-09-10). Survey read: README, docs/, _rule-workbench/, and three book dirs in full (clean-code, a-philosophy-of-software-design, working-effectively-with-legacy-code).

## What it is

14 rule sets distilled from classic software books (Clean Code, Refactoring, DDD ×3, APoSD, Clean Architecture, PoEAA, DDIA, Code Complete, Pragmatic Programmer, Release It!, WELC, Refactoring.Guru), each shipped in three sizes — `full` (canonical), `mini` ("the recommended version for most real task use"), `nano` ("the compact fallback for very tight context budgets") — packaged both as AGENTS.md-style rules and as one Agent Skill per book (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md). The interesting artifact is less the rules than the **_rule-workbench/**: an auditable agent-run pipeline that compresses each book, traces every surviving rule back to source, and scores all 91 book pairs for co-loading compatibility.

## How it works

### 1. Artifact structure — skills that point at rule files

Per book dir `<book>/`: `<book>.md` (full), `<book>.mini.md`, `<book>.nano.md`, `SKILL.md` (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md). `SKILL.md` is tiny (~600–800 B) — frontmatter `name`/`description`/`license` plus two sentences; it is a pure dispatcher that implements progressive disclosure (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/clean-code/SKILL.md):

> "Before making design or code decisions, read and apply [clean-code.mini.md](clean-code.mini.md). Use [clean-code.md](clean-code.md) only as a deeper reference when the mini rules are not enough."

So: description always in context → SKILL.md on invoke → mini read on demand → full only for deep dives. Install: `npx skills add ciembor/agent-rules-books --all` (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md). SKILL.md entrypoints were only added in v0.6 (2026-09-09) — the repo started as AGENTS.md rules and pivoted to skills packaging (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/CHANGELOG.md).

### 2. Rule file shape — one fixed template

Every mini/nano uses the same five-section shape defined in PROCESS.md "Preferred Output Shape": `# OBEY {book} by {author}` → When to use → Primary bias to correct → Decision rules → Trigger rules → Final checklist (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/PROCESS.md). Full files are richer (e.g. WELC full: Purpose, Primary Directive, Non-Negotiable Rules, Default Workflow, Seam Rules, Dependency Breaking Rules, Forbidden Patterns, Review Rules; clean-code full ends in "Hard rules": "Do not silently broaden scope beyond the requested task") (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/working-effectively-with-legacy-code/working-effectively-with-legacy-code.md, https://raw.githubusercontent.com/ciembor/agent-rules-books/main/clean-code/clean-code.md). Modal strength is standardized in ADDING_THE_BOOK step 3: "express obligations as `MUST`, strong defaults as `SHOULD`, prohibitions as `MUST NOT`, and keep anti-patterns explicit" (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/ADDING_THE_BOOK.md).

### 3. Workbench mechanics — compression as an auditable agent process

- **Generation** (docs/ADDING_THE_BOOK.md): chatbot extracts "every chapter, every section … and every operational rule stated or strongly implied", expands until nothing material is missing, emits a full file to the repo standard; a human reviews that "modal strength matches the book's intent, and that the chatbot did not invent unsupported rules"; then PROCESS.md and RELEASE.md run (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/ADDING_THE_BOOK.md).
- **Compression goal** (PROCESS.md): "Create compressed rule sets that are decision-equivalent to the full source, not sentence-equivalent." Each source rule is classified: `default` / `book-thesis` / `decision-changing` / `micro-decision` / `conflict-resolver` / `trigger` / `checklist-only` / `framing`. mini keeps every book-thesis, decision-changing, and conflict-resolver rule; nano keeps only rules "that correct known model biases": "shallow wrappers mistaken for good abstraction, framework-first design, unsafe retries, rewrite-first legacy work, fake DDD or fake layering, hidden consistency contracts" (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/PROCESS.md).
- **Evidence discipline**: "`default`" may only label rules "target agents reliably follow … you have evidence for that claim"; "Human-obvious is not the same as agent-default"; "Use the removal test: if deleting a rule is likely to bring back a known bad habit, keep it" (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/PROCESS.md).
- **Traceability**: each book gets `traceability.md` with `M*`/`N*` ids mapping every retained mini/nano rule to "the source section names and current line ranges in `full.md`"; every omitted rule gets "covered by Mx / covered by Nx / intentionally lost"; a mandatory section-coverage review walks every full section (kept / merged / kept only in nano / intentionally lost) (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/working-effectively-with-legacy-code/traceability.md). Example: WELC `M1` cites six full-file section line ranges.
- **Process over patches**: findings are diagnosed as `process bug` vs `book-specific miss`; "update `PROCESS.md` first … do not patch the book ad hoc to match reviewer taste"; "If you keep rediscovering the same omission class while reviewing different books, promote that lesson into `PROCESS.md`" (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/PROCESS.md).
- **Release** (RELEASE.md): canonical full is never edited ("Each workbench directory exposes it as `full.md` via symlink"); mini/nano are copied into the book dir; README gets a deterministic metrics table (wc -l lines, wc -c bytes, list-item rule count); traceability stays out of the public release surface (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/RELEASE.md).
- **Compatibility** (CHECK_COMPATIBILITY.md + COMPATIBILITY.md): "This is not a vibes-based comparison" — every unordered pair of the 14 minis gets a doc with Conflict/Overlap/Complementarity percentages, verdict ✅/❌/🔁, and cited line ranges; same-family pairs (e.g. refactoring vs refactoring-guru, clean-code vs code-complete) default to 🔁 unless proven distinct; "known tension pairs" (e.g. "a-philosophy-of-software-design vs clean-code: method length, comment philosophy, deep modules versus small-function pressure") require external research before `Status: reviewed` (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/CHECK_COMPATIBILITY.md). Result: 78 ✅ complementary, 11 🔁 overlap, 2 ❌ (PoEAA vs DDD and PoEAA vs IDDD) (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/COMPATIBILITY.md).

### 4. Consumption model and context cost

README ships a metrics table per book (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md); measured bytes → ~tokens (÷4) for the three surveyed books:

| Book | full | mini | nano |
| --- | --- | --- | --- |
| clean-code | 13,851 B (~3.5k tok) | 3,804 B (~950 tok) | 1,235 B (~310 tok) |
| a-philosophy-of-software-design | 13,557 B (~3.4k tok) | 5,774 B (~1.4k tok) | 2,258 B (~560 tok) |
| working-effectively-with-legacy-code | 13,812 B (~3.5k tok) | 5,707 B (~1.4k tok) | 1,792 B (~450 tok) |

Range across all 14: full 11–63 KB, mini 3.8–8.1 KB, nano 1.2–2.8 KB (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md). Loading policy (docs/USAGE.md): "Use the smallest mechanism that still changes the agent's decisions"; skill-from-mini is the "best default for most book-specific guidance"; "Need more than one book: keep one primary always-on rule set and move the rest to on-demand mechanisms"; avoid-lists per editor: "loading several `full` files globally", "pasting a long `full` rule file into root `CLAUDE.md`" (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/USAGE.md).

### 5. Evidence and honesty artifacts

One validation run (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md "Does it work?"): two refactors of the vibe-coded-crap helpdesk CLI — APoSD mini rules vs an AGENTS.md that only names the book. "ChatGPT rated the mini rules refactor at roughly 74/100, versus 46/100 for the branch that only mentioned the book", but a Reek smell check was nearly flat (1083 → 1077 smells). Self-labeled "an early qualitative signal, not a benchmark"; no further evals planned. docs/CRITICISM.md consolidates 13 Reddit criticisms with validity scores and self-assessed fix status: strongest unresolved are "There is no clear measurement of improvement" (validity 9/10, "about 2/10 solved") and "Rules should also come from real project failures" (8/10, "3/10 solved"); the legal item is bluntly quoted from the author — "it's a destilled content taken from ChatGPT. So OpenAI had stolen books, I distilled ChatGPT, will OpenAI sue me for this?" — with resolution policy "won't fix" beyond safer framing (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/CRITICISM.md).

## What to steal

1. **The three-tier sizing discipline (full/mini/nano + deterministic byte metrics).** Map directly onto our skills: SKILL.md body = mini-class payload (~1–1.5k tokens), reference files = full-class, and keep a published size column in our skill index so context cost is a first-class selection criterion (greenfield chain loads 4–6 skills per task; at ~1.4k tok/skill this matters). Source: https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md, https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/RELEASE.md.
2. **The fixed rule-file template: When to use / Primary bias to correct / Decision rules / Trigger rules / Final checklist.** This is the best 5-part skeleton I've seen for our brownfield guardrails and greenfield phase gates — "Trigger rules" (fire-on-condition) is exactly the bridge between our flow steps and decision pressure, and "Final checklist" gives agents a self-verify pass. Adopt as our authoring standard for rule-bearing skills (feeds T008). Source: https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/PROCESS.md.
3. **The compression/traceability process for authoring from corpora.** Classify rules (thesis/decision-changing/micro-decision/trigger…), require `M*`-style ids back to source, mark every drop as `covered by Mx` or `intentionally lost`, and require eval evidence before calling anything a "default" the model does anyway. Steal the epistemics ("Human-obvious is not the same as agent-default"; the removal test) even if we skip the paperwork. Source: https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/PROCESS.md.
4. **The nano known-model-bias list as the seed of our always-on layer.** Their six biases — shallow wrappers, framework-first design, unsafe retries, rewrite-first legacy work, fake DDD/layering, hidden consistency contracts — are exactly the failure modes our greenfield/brownfield flow must police; a ~300–600 token baseline derived from these is cheap and high-yield. Source: https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/PROCESS.md (Build nano.md).
5. **WELC mini as ready-made brownfield decision pressure.** Its core loop is our brownfield chain in compressed form: "Gain control before improving design"; characterize-before-redesign; smallest seam; "Keep behavior changes, structural refactorings, and cleanup separate"; Forbidden Patterns: "Rewrite as the First Move", "No-Safety Change", "Cosmetic Refactoring Only". Either vendor the file as reference material or compress its 15 decision rules into our brownfield skill. Source: https://raw.githubusercontent.com/ciembor/agent-rules-books/main/working-effectively-with-legacy-code/working-effectively-with-legacy-code.mini.md, https://raw.githubusercontent.com/ciembor/agent-rules-books/main/working-effectively-with-legacy-code/working-effectively-with-legacy-code.md.
6. **APoSD mini as greenfield module-design pressure.** Deep modules over shallow wrappers; "When adding a module, layer, service, helper, wrapper, facade, pattern, option, callback, or argument, prove that it hides more complexity than it adds" — the single best anti-overengineering line for the greenfield build phase, matching their anti-ceremony criticism fix. Source: https://raw.githubusercontent.com/ciembor/agent-rules-books/main/a-philosophy-of-software-design/a-philosophy-of-software-design.mini.md.
7. **The compatibility-matrix pattern, in miniature.** We don't need 91 pair docs, but we do need a co-loading policy per skill (which skills may co-activate, which one arbitrates on conflict) plus the "one primary, rest on-demand" rule for multi-skill tasks. Their taxonomy (complementary/overlap/conflict) is enough. Source: https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/COMPATIBILITY.md, https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/USAGE.md.
8. **A CRITICISM.md for our own skillset.** Self-scored weaknesses with validity ratings and honest "about 2/10 solved" statuses is an unusually good honesty artifact for a skill repo we'll iterate on. Source: https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/CRITICISM.md.

## What to skip

1. **Adopting the corpus itself (14 books) as our content.** Our skillset's product is the flow (procedures, tickets, gates), not style guidance; book rules are a content layer we can borrow per-need (WELC, APoSD) rather than maintain. Also unmeasured: their own top criticism is "no clear measurement of improvement" (9/10 validity, weakly addressed), and the only experiment is one ChatGPT-judged refactor of one vibe-coded CLI (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md, https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/CRITICISM.md).
2. **Legal-risky derivation chains.** The rules were extracted from books via ChatGPT; the author's own CRITICISM.md flags this and adopts framing-only mitigation ("won't fix"). If we ever vendor book-derived rules, do it as clearly-labeled third-party dependencies (npx-installable), not as content we fork and relicense (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/CRITICISM.md item 11).
3. **The 91-pair compatibility matrix and symlink workbench.** Pair docs with % scores are a maintenance sink and are self-admittedly "qualitative and source-based, not validated by empirical task runs" (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/CRITICISM.md item 7). Symlinked `full.md` also travels poorly; a plain copy + CI size check achieves the same invariant (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/RELEASE.md).
4. **AGENTS.md always-on as the primary delivery.** The repo's own conclusion is skills-first with at most one mini/nano always-on (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/USAGE.md). Our skillset is already skills; at most we add one ~300–600 token nano-style baseline file, not an AGENTS.md rules layer.
5. **nano as a separate released artifact per skill.** nano exists for "always-on" budgets, which only matters if we ship an always-on layer; progressive disclosure already bounds per-skill cost. Decide after the greenfield/brownfield chains are measured, not by default (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/USAGE.md Mini vs Nano).

## Rules-books pattern alongside skills — the decision

Yes, adopt the **pattern**, not the corpus, and the interaction is exactly what this repo implements: **SKILL.md = dispatcher (procedure), rule file = payload (decision pressure), full = reference.** A skill encodes how to run a step of the flow; a rule book encodes what to prefer when choosing inside that step. The clean seam is a one-line pointer in the skill body ("Before X, read and apply <rules.md>") — the same sentence their SKILL.md uses — so rule payloads stay swappable and sized independently of skill logic. Concretely for us: (a) standardize rule-bearing sections of our skills on their 5-part template; (b) optionally vendor WELC-mini (brownfield) and APoSD-mini (greenfield design) as reference files behind our existing skills rather than as standalone skills; (c) add the "one primary rule set, rest on-demand" co-loading policy to our flow docs.

## Surprises & open questions

- **The workbench is the product.** PROCESS.md is itself an agent-facing prompt (like our ticket system): agents do the compression, humans review modal strength, findings feed back into the process file instead of ad-hoc patches. This is the same loop as our MAP/tickets/refine setup, independently invented. (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/_rule-workbench/PROCESS.md)
- **The repo pivoted to skills only in v0.6** (2026-09-09): "Added standard `SKILL.md` entrypoints for every book rule set" — until then it was AGENTS.md rules only. The rules-vs-skills framing in its title is that history. (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/CHANGELOG.md)
- **Unusual honesty artifacts:** CRITICISM.md self-scores weaknesses ("about 2/10 solved"), and the README's own experiment reports a null static-analysis result next to its positive LLM-judge result. (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/docs/CRITICISM.md, https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md)
- Open: does anything beyond one vibe-coded CLI validate mini rules? "Deeper measurements and equivalent experiments for other books are not planned at this stage." (https://raw.githubusercontent.com/ciembor/agent-rules-books/main/README.md)
- Open: obedience under co-loading — they recommend one primary book per task but never measure whether two minis (~3k tokens) degrade each other; our multi-skill chains face the same untested assumption.
- Open for us: traceability cites line ranges that "drift" on edit (CHECK_COMPATIBILITY.md: "Refresh line citations if the source files change") — if we adopt M*-id traceability, cite section names, not line numbers.
